Краткий вывод

Сервис дорожной помощи для Алжира: клиент, водитель, админка, реалтайм-карта, чат, пуши. Для проекта такого размера архитектура на удивление аккуратная — цена считается только на сервере, статусы заказа ходят по явной таблице переходов, документы водителя невозможно одобрить самому себе. Это не набросок, это продуманная система.

Но между «продумано» и «выдержит боевую нагрузку» есть разрыв, и он в трёх местах:

  1. Админка собирает HTML строками из данных, которые вводит любой желающий. Регистрация водителя — открытая форма. Фамилия водителя попадает в innerHTML админки без экранирования. Это не теоретический XSS: чтобы одобрить водителя, админ обязан открыть эту карточку. Полный захват админского аккаунта одной заявкой.
  1. Появилось поле availability, но старое isOnline никто не убрал. Поиск водителей смотрит на новое поле, расчёт цены — на старое. Занятый водитель принимает второй заказ. Проверено тестом.
  1. Приложение считает, что телефон водителя всегда на экране и разблокирован. Геолокация шлётся setInterval'ом раз в 5 секунд из foreground. Водитель включает навигацию — грузовик на карте клиента замирает. Это не оптимизация, это ядро продукта.

Ни одна из трёх не требует переписывания. Первая — одна функция экранирования, вторая — одна строка в quote(), третья — переход на expo-task-manager.

0. Что не надо трогать

Шесть вещей сделаны правильно, и правильно по неочевидным причинам:

  • Цену нельзя подделать. Клиент присылает только координаты; priceFromDistances считает на сервере и кладёт tariffSnapshot в заказ — историю не переписать задним числом при смене тарифа. Покрыто тестом. — src/services/pricing.js:77, src/services/orders.js:59
  • Машина состояний — таблица, а не набор if. TRANSITIONS явно перечисляет разрешённые переходы, права проверяются отдельно от перехода. Перепрыгнуть requested → delivered нельзя. — src/services/orders.js:10–20
  • Водитель не может одобрить себя сам. withPendingDocs принудительно ставит любому присланному документу status: 'pending', а схема Zod физически не даёт прислать поле status. Два барьера на одну угрозу — так и надо. — src/routes/index.js:315
  • Удаление аккаунта — анонимизация, а не DELETE. Заказы и чаты второй стороны остаются целыми, персональные данные стираются. Это осознанное решение, и оно верное. — src/db/pg.js:198
  • Один пуш-токен = один аккаунт. clearPushTokenForOthers снимает токен со всех остальных при входе. Мелочь, о которой обычно вспоминают после первой жалобы «мне приходят чужие заказы». — src/db/pg.js:144
  • Сервис не падает от внешних сбоев. OSRM, Nominatim, карта, пуши — у каждого свой фолбэк. Приложение продолжает работать при недоступности любого из них.

1. Критичные

C1КРИТИЧНОадминка: XSS из формы регистрации водителя → захват аккаунта админа

cardHtml() собирает карточку водителя конкатенацией строк и присваивает в innerHTML. Экранирования нет ни у одного поля:

// src/admin/index.html:218, 237
<div class="card-title">${name}</div>          // firstName + lastName
<div class="field"><b>Описание</b>${d.description}</div>

firstName, lastName, plateNumber, wilaya, description, phones, email приходят из POST /api/drivers/register — открытой формы, доступной любому, кто скачал приложение. Zod проверяет только длину: lastName до 60 символов, description до 1000. Полезная нагрузка вида <img src=x onerror=...> укладывается в 36 символов.

Ключевая деталь: карточка отображается на вкладке «Заявки», и админ обязан её открыть, чтобы нажать «Одобрить». Payload срабатывает гарантированно, при обычной работе.

Дальше идёт цепочка, где каждое звено усиливает предыдущее:

  • CSP для /admin отключён вручную. default-src 'self' 'unsafe-inline' data: blob: * и connect-src * — helmet ставит нормальную политику, а этот роут её перетирает. Инлайн-скрипты разрешены, отправка данных на любой домен разрешена. — src/app.js:79
  • Админский JWT лежит в localStorage — доступен любому скрипту на странице. — src/admin/index.html:109
  • Токен подставляется в src каждой картинки: imgUrl() даёт /api/files/xxx.jpg?token=<JWT>. Токен утекает не только через XSS, но и в access-логи nginx на каждый просмотр документа. — src/admin/index.html:113

Итог: заявка водителя → выполнение произвольного кода в админке → админский токен на 7 дней без возможности отзыва → изменение тарифов, доступ к паспортам всех водителей, блокировка кого угодно.

Что сделать.

  1. Функция esc(s) (String(s).replace(/[&<>"']/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]))) и обернуть в неё каждую интерполяцию в cardHtml, tripCard, renderDrivers, renderTariffs. Правка механическая, риска не несёт.
  2. Убрать * и 'unsafe-inline' из CSP админки. Скрипт вынести в отдельный файл — тогда script-src 'self' работает, и XSS перестаёт быть исполняемым даже при промахе в п.1.
  3. Токен админки — в httpOnly-cookie, а не в localStorage. Из ?token= в URL картинок убрать: отдавать документы через fetch с заголовком и URL.createObjectURL.

C2КРИТИЧНОсервер стартует с зашитым JWT-секретом, если .env не подхватился

// src/middleware/auth.js:12
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-change-me';

Секрет опубликован в исходниках. Если .env не прочитался — переименовали файл, потеряли при переносе на новый сервер, source .env не отработал в деплое — сервер поднимется молча, /health вернёт ok, и всё будет работать. Ровно до момента, когда кто-то подпишет себе {"sub":"<любой id>","role":"admin"} этим общеизвестным секретом.

Деплой делает set -a; source .env; set +a (.github/workflows/deploy.yml) — то есть переменные живут ровно в этой SSH-сессии и зависят от того, что файл на месте и без опечаток.

Что сделать. Падать на старте, а не подставлять заглушку:

const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET || JWT_SECRET.length < 32) {
  throw new Error('JWT_SECRET не задан или короче 32 символов');
}

Для тестов — задать переменную в package.json, как уже сделано с OSRM_TIMEOUT_MS. Заодно добавить в токен tokenVersion из БД, чтобы существующие токены можно было отозвать.

C3КРИТИЧНОлюбой клиент видит GPS любого водителя в реальном времени

// src/services/realtime.js:73
socket.on('watch:driver', (driverId) => {
  if (typeof driverId === 'string') socket.join(`driver-watch:${driverId}`);
});

Проверяется только тип аргумента. Ни участия в заказе, ни существования водителя, ни лимита на количество подписок.

Соседний обработчик join:order делает нужную проверку — там честно грузится заказ и сверяется участник (realtime.js:83–93). То есть про эту угрозу думали, а на watch:driver не распространили.

Идентификаторы водителей раздаёт GET /api/drivers/nearby любому клиенту — то есть их не надо даже угадывать. Клиент подписывается на всех разом и получает непрерывный поток координат всего парка: где живёт водитель, когда заканчивает смену, где стоит ночью. Для сервиса, где водители — частные лица со своими эвакуаторами, это прямая угроза их безопасности.

Что сделать. Та же проверка, что в join:order: подписка разрешена, только если у подписчика есть активный заказ с этим водителем.

socket.on('watch:driver', async (driverId) => {
  if (typeof driverId !== 'string' || role !== 'client') return;
  const active = (await db.orders.byClient(id))
    .find(o => o.driverId === driverId && ['requested','accepted','arrived','en_route'].includes(o.status));
  if (active) socket.join(`driver-watch:${driverId}`);
});

И отписывать при смене статуса заказа на терминальный — сейчас unwatch шлёт только клиент, по своей воле.

2. Высокие

H1ВЫСОКИЙзанятый водитель принимает второй заказ [проверено]

Два поля описывают одно и то же состояние, и разные части кода смотрят на разные:

МестоПроверяет
drivers.activeOnline() — поиск рядомavailability = 'online'
quote() — создание заказаisOnline === true

Когда водитель принимает заказ, /orders/:id/accept ставит availability: 'busy', а isOnline не трогает — оно остаётся true (src/routes/index.js:516). Из поиска водитель пропадает, но quote() его по-прежнему считает доступным.

Достаточно передать driverId напрямую в POST /api/orders — из своей же истории заказов, из кэша экрана, из ответа /drivers/nearby секундой раньше:

Клиент A заказывает водителя D  → D принимает → availability=busy, isOnline=true
Клиент B шлёт POST /api/orders { driverId: D }  → 201 Created

Проверено интеграционным тестом: второй заказ создаётся со статусом 201. Водитель получает пуш о новом заказе, находясь под машиной первого клиента. Ошибка DRIVER_UNAVAILABLE, ради которой всё писалось, не срабатывает никогда.

Адрес: src/services/orders.js:27 · src/routes/index.js:516

Что сделать. В quote() проверять то же поле, что и поиск:

if (driver.status !== 'active' || driver.availability !== 'online') {
  throw new Error('DRIVER_UNAVAILABLE');
}

И убрать isOnline совсем — оно осталось от предыдущей модели и сейчас только вводит в заблуждение (в /admin/stats счётчик «онлайн» тоже считает по нему, то есть показывает онлайн + занятых). Миграция: UPDATE drivers SET availability = CASE WHEN is_online THEN 'online' ELSE 'offline' END уже есть в schema.sql:163, осталось удалить колонку.

Отдельно: между quote() и db.orders.create() нет блокировки, поэтому два одновременных запроса всё равно проскочат. Правильное решение — условный UPDATE: UPDATE drivers SET availability='busy' WHERE id=$1 AND availability='online' RETURNING id, и создавать заказ только если вернулась строка.

H2ВЫСОКИЙкод сброса пароля можно перебрать

Строгий лимит (30 попыток / 15 минут) висит ровно на трёх путях:

// src/app.js:69–71
app.use('/api/auth/login', authLimiter);
app.use('/api/auth/register', authLimiter);
app.use('/api/auth/admin-login', authLimiter);

/auth/reset-password и /auth/verify-email под ним нет — на них действует общий лимит 600 запросов в минуту. Код шестизначный, checkResetCode не считает неудачные попытки и не гасит код после промаха (src/db/pg.js:184).

Считаем: 600 попыток/мин × 15 минут жизни кода = 9 000 попыток на окно из 1 000 000 — 0,9% за один цикл. Но /auth/forgot-password тоже без лимита, а каждый вызов выдаёт новый код и продлевает окно. Атака идёт непрерывно; с десятка адресов аккаунт вскрывается за часы. Успех даёт не только смену пароля — эндпоинт сразу возвращает валидный JWT (routes/index.js:250).

Дополнительно: setVerifyCode и setResetCode пишут в одну колонку verify_code (src/db/pg.js:148 и :180). Код подтверждения почты и код сброса пароля — это один и тот же секрет с разными правами. Запрос подтверждения почты затирает активный код сброса и наоборот.

Что сделать.

  1. authLimiter на /auth/forgot-password, /auth/reset-password, /auth/verify-email, /auth/send-code.
  2. Счётчик попыток в БД: verify_attempts, после 5 неудач код гасится (verify_code = NULL).
  3. Разнести колонки: reset_code/reset_expires отдельно от verify_code/verify_expires.
  4. Код из 6 цифр — 20 бит энтропии. Либо 8 символов, либо одноразовая ссылка с 128-битным токеном.

H3ВЫСОКИЙфоновая задача читает всю таблицу заказов каждые 5 секунд

// src/services/jobs.js:28, 80
const orders = await db.orders.all();     // SELECT * FROM orders ORDER BY created_at DESC
for (const o of orders) { if (o.status !== 'requested') continue; ... }
setInterval(() => expireStaleOrders().catch(() => {}), 5 * 1000);

Каждые 5 секунд из базы вычитываются все заказы за всю историю — с breakdown и tariff_snapshot в JSONB — чтобы найти те несколько, что висят в requested. Отбор идёт в JavaScript. autoConfirmDelivered делает то же самое раз в минуту.

На старте это незаметно. При 50 000 заказов — 50 000 строк каждые 5 секунд, 10 000 строк/сек постоянной нагрузки на базу и на GC Node, ради задачи, которая обычно не находит ничего. При instances: 1 в PM2 (ecosystem.config.cjs) это тот же процесс, что обслуживает пользователей: сборка мусора после каждого прохода бьёт по латентности всех запросов.

Что сделать. Перенести отбор в SQL — задача превращается в один точечный запрос по индексу:

UPDATE orders SET status = 'expired'
 WHERE status = 'requested' AND accept_deadline < now() - interval '5 seconds'
 RETURNING id, client_id, driver_id;
CREATE INDEX idx_orders_pending ON orders(accept_deadline) WHERE status = 'requested';
CREATE INDEX idx_orders_delivered ON orders(delivered_at) WHERE status = 'delivered';

expireSubscriptions — то же самое, WHERE status='active' AND subscription_end < now().

H4ВЫСОКИЙрейтинг водителя накручивается повторными оценками [проверено]

POST /orders/:id/rating проверяет владельца и статус заказа, но **не проверяет, оценивал ли клиент этот заказ раньше**:

// src/routes/index.js:593–604
if (order.status !== 'completed') return res.status(409).json({ error: 'ORDER_NOT_COMPLETED' });
const rating = await db.ratings.create({ ... });   // проверки на дубль нет

ratings.create после вставки пересчитывает rating_avg водителя по всем строкам.

Проверено тестом: 10 запросов с одной звездой по одному заказу → ratingCount: 10, средний рейтинг водителя падает с 5.0 до 1.0. Один недовольный клиент опускает водителя на дно выдачи; один сговорчивый — поднимает на верх.

Соседний эндпоинт rate-client дубль проверяет (routes/index.js:613) — асимметрия, значит просто забыли.

В PostgreSQL есть UNIQUE(order_id) (schema.sql:107), поэтому там накрутка не пройдёт — но необработанное нарушение констрейнта уйдёт в общий обработчик ошибок и вернёт клиенту 500 INTERNAL_ERROR вместо понятного «уже оценено». А тесты гоняются на in-memory, где констрейнта нет, и потому молчат.

Что сделать. Явная проверка в роуте + корректный код ответа:

const existing = await db.ratings.byOrder(order.id);
if (existing) return res.status(409).json({ error: 'ALREADY_RATED' });

и UNIQUE-индекс продублировать в in-memory реализации, чтобы тесты ловили расхождение.

H5ВЫСОКИЙв приложении нет удаления аккаунта → отклонение в Google Play

Бэкенд реализован полностью и грамотно — DELETE /api/auth/account с анонимизацией, и в комментарии прямо написано «требование Google Play» (src/routes/index.js:260).

В приложении этот эндпоинт не вызывается ни разу. Поиск по всему depanini-app по auth/account и deleteAccount — ноль совпадений. В ProfileScreen есть смена аватара, язык, тема, тестовый пуш и выход — удаления нет.

Синхронный scrypt с параметрами по умолчанию (N=16384) занимает ~80–100 мс CPU. Node однопоточный: всё это время сервер не обрабатывает ничего — ни заказы, ни позиции водителей, ни health-check. Десять одновременных входов — секунда полной заморозки.

Это же делает вход бесплатным вектором DoS: 30 запросов в 15 минут на IP (authLimiter) с десятка адресов дают устойчивую нагрузку в 100% одного ядра.

Что сделать. Асинхронный вариант — crypto.scrypt через promisify. Работа уходит в пул потоков libuv, цикл событий свободен. Правка на три строки, интерфейс функций не меняется.

M15СРЕДНИЙФайлы лежат на локальном диске одного инстанса

UPLOAD_DIR по умолчанию — папка uploads рядом с кодом (src/services/uploads.js:19), PM2 запущен в fork с instances: 1 (ecosystem.config.cjs). Значит:

  • горизонтально масштабироваться нельзя — второй инстанс не увидит файлы первого;
  • переезд на новый сервер = потеря всех документов водителей, если не помнить про rsync;
  • бэкапа нет, ротации нет: перезалитые документы остаются на диске навсегда;
  • падение процесса = недоступность сервиса целиком (нет второго инстанса).

Плюс fileFilter доверяет file.mimetype, который приходит из запроса — расширение выбирается по нему же. Реальные байты не проверяются.

Что сделать. S3-совместимое хранилище (в .env.example переменные уже заведены) — и файлы переживают деплой, и инстансов можно поднять несколько. Проверять сигнатуру файла по первым байтам, а не по заголовку. Чистить осиротевшие файлы при перезаливке документа.

Что сделать. Пропускать пустые поля (if (el && el.value !== '') ...), поднять нижнюю границу в схеме (min(1) для pricePerKm, minFare), показывать подтверждение при снижении тарифа более чем вдвое. M17СРЕДНИЙПуш-уведомления: нет пакетной отправки и очистки мёртвых токенов

sendPush шлёт по одному сообщению за запрос (src/services/push.js:39) и возвращает res.ok. Expo отвечает 200 даже когда доставка не удалась — детали лежат в теле ответа (DeviceNotRegistered, MessageTooBig), которое не читается. Квитанции (receipts) не запрашиваются.

Что сделать. Батч по 100 сообщений (Expo это поддерживает), разбор тела ответа, push_token = NULL при DeviceNotRegistered, опрос квитанций через 15 минут.
