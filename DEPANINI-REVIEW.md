## Краткий вывод

Сервис дорожной помощи для Алжира: клиент, водитель, админка, реалтайм-карта, чат, пуши.
Для проекта такого размера архитектура на удивление аккуратная — цена считается только на
сервере, статусы заказа ходят по явной таблице переходов, документы водителя невозможно
одобрить самому себе. Это не набросок, это продуманная система.

Но между «продумано» и «выдержит боевую нагрузку» есть разрыв, и он в трёх местах:

1. **Админка собирает HTML строками из данных, которые вводит любой желающий.** Регистрация
   водителя — открытая форма. Фамилия водителя попадает в `innerHTML` админки без экранирования.
   Это не теоретический XSS: чтобы одобрить водителя, админ **обязан** открыть эту карточку.
   Полный захват админского аккаунта одной заявкой.

2. **Появилось поле `availability`, но старое `isOnline` никто не убрал.** Поиск водителей
   смотрит на новое поле, расчёт цены — на старое. Занятый водитель принимает второй заказ.
   Проверено тестом.

3. **Приложение считает, что телефон водителя всегда на экране и разблокирован.** Геолокация
   шлётся `setInterval`'ом раз в 5 секунд из foreground. Водитель включает навигацию — грузовик
   на карте клиента замирает. Это не оптимизация, это ядро продукта.

Ни одна из трёх не требует переписывания. Первая — одна функция экранирования, вторая —
одна строка в `quote()`, третья — переход на `expo-task-manager`.

## 0. Что не надо трогать

Шесть вещей сделаны правильно, и правильно по неочевидным причинам:

- **Цену нельзя подделать.** Клиент присылает только координаты; `priceFromDistances` считает
  на сервере и кладёт `tariffSnapshot` в заказ — историю не переписать задним числом при смене
  тарифа. Покрыто тестом. — `src/services/pricing.js:77`, `src/services/orders.js:59`
- **Машина состояний — таблица, а не набор `if`.** `TRANSITIONS` явно перечисляет разрешённые
  переходы, права проверяются отдельно от перехода. Перепрыгнуть `requested → delivered`
  нельзя. — `src/services/orders.js:10–20`
- **Водитель не может одобрить себя сам.** `withPendingDocs` принудительно ставит любому
  присланному документу `status: 'pending'`, а схема Zod физически не даёт прислать поле
  `status`. Два барьера на одну угрозу — так и надо. — `src/routes/index.js:315`
- **Удаление аккаунта — анонимизация, а не `DELETE`.** Заказы и чаты второй стороны остаются
  целыми, персональные данные стираются. Это осознанное решение, и оно верное. — `src/db/pg.js:198`
- **Один пуш-токен = один аккаунт.** `clearPushTokenForOthers` снимает токен со всех остальных
  при входе. Мелочь, о которой обычно вспоминают после первой жалобы «мне приходят чужие
  заказы». — `src/db/pg.js:144`
- **Сервис не падает от внешних сбоев.** OSRM, Nominatim, карта, пуши — у каждого свой фолбэк.
  Приложение продолжает работать при недоступности любого из них.

## 1. Критичные

### C1 · КРИТИЧНО — админка: XSS из формы регистрации водителя → захват аккаунта админа

`cardHtml()` собирает карточку водителя конкатенацией строк и присваивает в `innerHTML`.
Экранирования нет ни у одного поля:

```js
// src/admin/index.html:218, 237
<div class="card-title">${name}</div>          // firstName + lastName
<div class="field"><b>Описание</b>${d.description}</div>
```

`firstName`, `lastName`, `plateNumber`, `wilaya`, `description`, `phones`, `email` приходят из
`POST /api/drivers/register` — открытой формы, доступной любому, кто скачал приложение. Zod
проверяет только длину: `lastName` до 60 символов, `description` до 1000. Полезная нагрузка
вида `<img src=x onerror=...>` укладывается в 36 символов.

Ключевая деталь: карточка отображается на вкладке **«Заявки»**, и админ обязан её открыть,
чтобы нажать «Одобрить». Payload срабатывает гарантированно, при обычной работе.

Дальше идёт цепочка, где каждое звено усиливает предыдущее:

- **CSP для `/admin` отключён вручную.** `default-src 'self' 'unsafe-inline' data: blob: *`
  и `connect-src *` — helmet ставит нормальную политику, а этот роут её перетирает. Инлайн-скрипты
  разрешены, отправка данных на любой домен разрешена. — `src/app.js:79`
- **Админский JWT лежит в `localStorage`** — доступен любому скрипту на странице. — `src/admin/index.html:109`
- **Токен подставляется в `src` каждой картинки:** `imgUrl()` даёт `/api/files/xxx.jpg?token=<JWT>`.
  Токен утекает не только через XSS, но и в access-логи nginx на каждый просмотр документа. — `src/admin/index.html:113`

Итог: заявка водителя → выполнение произвольного кода в админке → админский токен на 7 дней
без возможности отзыва → изменение тарифов, доступ к паспортам всех водителей, блокировка кого угодно.

**Что сделать.**
1. Функция `esc(s)` (`String(s).replace(/[&<>"']/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]))`)
   и обернуть в неё **каждую** интерполяцию в `cardHtml`, `tripCard`, `renderDrivers`, `renderTariffs`.
   Правка механическая, риска не несёт.
2. Убрать `*` и `'unsafe-inline'` из CSP админки. Скрипт вынести в отдельный файл — тогда
   `script-src 'self'` работает, и XSS перестаёт быть исполняемым даже при промахе в п.1.
3. Токен админки — в `httpOnly`-cookie, а не в `localStorage`. Из `?token=` в URL картинок
   убрать: отдавать документы через `fetch` с заголовком и `URL.createObjectURL`.

### C2 · КРИТИЧНО — сервер стартует с зашитым JWT-секретом, если `.env` не подхватился

```js
// src/middleware/auth.js:12
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-change-me';
```

Секрет опубликован в исходниках. Если `.env` не прочитался — переименовали файл, потеряли при
переносе на новый сервер, `source .env` не отработал в деплое — сервер поднимется **молча**,
`/health` вернёт `ok`, и всё будет работать. Ровно до момента, когда кто-то подпишет себе
`{"sub":"<любой id>","role":"admin"}` этим общеизвестным секретом.

Деплой делает `set -a; source .env; set +a` (`.github/workflows/deploy.yml`) — то есть переменные
живут ровно в этой SSH-сессии и зависят от того, что файл на месте и без опечаток.

**Что сделать.** Падать на старте, а не подставлять заглушку:

```js
const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET || JWT_SECRET.length < 32) {
  throw new Error('JWT_SECRET не задан или короче 32 символов');
}
```

Для тестов — задать переменную в `package.json`, как уже сделано с `OSRM_TIMEOUT_MS`.
Заодно добавить в токен `tokenVersion` из БД, чтобы существующие токены можно было отозвать.

### C3 · КРИТИЧНО — любой клиент видит GPS любого водителя в реальном времени

```js
// src/services/realtime.js:73
socket.on('watch:driver', (driverId) => {
  if (typeof driverId === 'string') socket.join(`driver-watch:${driverId}`);
});
```

Проверяется только тип аргумента. Ни участия в заказе, ни существования водителя, ни лимита
на количество подписок.

Соседний обработчик `join:order` **делает** нужную проверку — там честно грузится заказ и
сверяется участник (`realtime.js:83–93`). То есть про эту угрозу думали, а на `watch:driver`
не распространили.

Идентификаторы водителей раздаёт `GET /api/drivers/nearby` любому клиенту — то есть их не надо
даже угадывать. Клиент подписывается на всех разом и получает непрерывный поток координат
всего парка: где живёт водитель, когда заканчивает смену, где стоит ночью. Для сервиса, где
водители — частные лица со своими эвакуаторами, это прямая угроза их безопасности.

**Что сделать.** Та же проверка, что в `join:order`: подписка разрешена, только если у
подписчика есть активный заказ с этим водителем.

```js
socket.on('watch:driver', async (driverId) => {
  if (typeof driverId !== 'string' || role !== 'client') return;
  const active = (await db.orders.byClient(id))
    .find(o => o.driverId === driverId && ['requested','accepted','arrived','en_route'].includes(o.status));
  if (active) socket.join(`driver-watch:${driverId}`);
});
```

И отписывать при смене статуса заказа на терминальный — сейчас `unwatch` шлёт только клиент,
по своей воле.

## 2. Высокие

### H1 · ВЫСОКИЙ — занятый водитель принимает второй заказ **[проверено]**

Два поля описывают одно и то же состояние, и разные части кода смотрят на разные:

| Место | Проверяет |
|---|---|
| `drivers.activeOnline()` — поиск рядом | `availability = 'online'` |
| `quote()` — создание заказа | `isOnline === true` |

Когда водитель принимает заказ, `/orders/:id/accept` ставит `availability: 'busy'`,
а `isOnline` **не трогает** — оно остаётся `true` (`src/routes/index.js:516`). Из поиска
водитель пропадает, но `quote()` его по-прежнему считает доступным.

Достаточно передать `driverId` напрямую в `POST /api/orders` — из своей же истории заказов,
из кэша экрана, из ответа `/drivers/nearby` секундой раньше:

```
Клиент A заказывает водителя D  → D принимает → availability=busy, isOnline=true
Клиент B шлёт POST /api/orders { driverId: D }  → 201 Created
```

Проверено интеграционным тестом: второй заказ создаётся со статусом 201. Водитель получает
пуш о новом заказе, находясь под машиной первого клиента. Ошибка `DRIVER_UNAVAILABLE`,
ради которой всё писалось, не срабатывает никогда.

*Адрес:* `src/services/orders.js:27` · `src/routes/index.js:516`

**Что сделать.** В `quote()` проверять то же поле, что и поиск:

```js
if (driver.status !== 'active' || driver.availability !== 'online') {
  throw new Error('DRIVER_UNAVAILABLE');
}
```

И убрать `isOnline` совсем — оно осталось от предыдущей модели и сейчас только вводит в
заблуждение (в `/admin/stats` счётчик «онлайн» тоже считает по нему, то есть показывает
онлайн + занятых). Миграция: `UPDATE drivers SET availability = CASE WHEN is_online THEN 'online' ELSE 'offline' END` уже
есть в `schema.sql:163`, осталось удалить колонку.

Отдельно: между `quote()` и `db.orders.create()` нет блокировки, поэтому два одновременных
запроса всё равно проскочат. Правильное решение — условный `UPDATE`:
`UPDATE drivers SET availability='busy' WHERE id=$1 AND availability='online' RETURNING id`,
и создавать заказ только если вернулась строка.

### H2 · ВЫСОКИЙ — код сброса пароля можно перебрать

Строгий лимит (30 попыток / 15 минут) висит ровно на трёх путях:

```js
// src/app.js:69–71
app.use('/api/auth/login', authLimiter);
app.use('/api/auth/register', authLimiter);
app.use('/api/auth/admin-login', authLimiter);
```

`/auth/reset-password` и `/auth/verify-email` под ним нет — на них действует общий лимит
**600 запросов в минуту**. Код шестизначный, `checkResetCode` не считает неудачные попытки
и не гасит код после промаха (`src/db/pg.js:184`).

Считаем: 600 попыток/мин × 15 минут жизни кода = 9 000 попыток на окно из 1 000 000 — 0,9%
за один цикл. Но `/auth/forgot-password` тоже без лимита, а каждый вызов выдаёт **новый** код
и продлевает окно. Атака идёт непрерывно; с десятка адресов аккаунт вскрывается за часы.
Успех даёт не только смену пароля — эндпоинт сразу возвращает валидный JWT (`routes/index.js:250`).

Дополнительно: `setVerifyCode` и `setResetCode` пишут в **одну колонку** `verify_code`
(`src/db/pg.js:148` и `:180`). Код подтверждения почты и код сброса пароля — это один и тот же
секрет с разными правами. Запрос подтверждения почты затирает активный код сброса и наоборот.

**Что сделать.**
1. `authLimiter` на `/auth/forgot-password`, `/auth/reset-password`, `/auth/verify-email`, `/auth/send-code`.
2. Счётчик попыток в БД: `verify_attempts`, после 5 неудач код гасится (`verify_code = NULL`).
3. Разнести колонки: `reset_code`/`reset_expires` отдельно от `verify_code`/`verify_expires`.
4. Код из 6 цифр — 20 бит энтропии. Либо 8 символов, либо одноразовая ссылка с 128-битным токеном.

### H3 · ВЫСОКИЙ — фоновая задача читает всю таблицу заказов каждые 5 секунд

```js
// src/services/jobs.js:28, 80
const orders = await db.orders.all();     // SELECT * FROM orders ORDER BY created_at DESC
for (const o of orders) { if (o.status !== 'requested') continue; ... }
setInterval(() => expireStaleOrders().catch(() => {}), 5 * 1000);
```

Каждые 5 секунд из базы вычитываются **все заказы за всю историю** — с `breakdown` и
`tariff_snapshot` в JSONB — чтобы найти те несколько, что висят в `requested`. Отбор идёт
в JavaScript. `autoConfirmDelivered` делает то же самое раз в минуту.

На старте это незаметно. При 50 000 заказов — 50 000 строк каждые 5 секунд, 10 000 строк/сек
постоянной нагрузки на базу и на GC Node, ради задачи, которая обычно не находит ничего.
При `instances: 1` в PM2 (`ecosystem.config.cjs`) это тот же процесс, что обслуживает
пользователей: сборка мусора после каждого прохода бьёт по латентности всех запросов.

**Что сделать.** Перенести отбор в SQL — задача превращается в один точечный запрос по индексу:

```sql
UPDATE orders SET status = 'expired'
 WHERE status = 'requested' AND accept_deadline < now() - interval '5 seconds'
 RETURNING id, client_id, driver_id;
```

```sql
CREATE INDEX idx_orders_pending ON orders(accept_deadline) WHERE status = 'requested';
CREATE INDEX idx_orders_delivered ON orders(delivered_at) WHERE status = 'delivered';
```

`expireSubscriptions` — то же самое, `WHERE status='active' AND subscription_end < now()`.

### H4 · ВЫСОКИЙ — рейтинг водителя накручивается повторными оценками **[проверено]**

`POST /orders/:id/rating` проверяет владельца и статус заказа, но **не проверяет, оценивал ли
клиент этот заказ раньше**:

```js
// src/routes/index.js:593–604
if (order.status !== 'completed') return res.status(409).json({ error: 'ORDER_NOT_COMPLETED' });
const rating = await db.ratings.create({ ... });   // проверки на дубль нет
```

`ratings.create` после вставки пересчитывает `rating_avg` водителя по всем строкам.

Проверено тестом: 10 запросов с одной звездой по одному заказу → `ratingCount: 10`,
средний рейтинг водителя падает с 5.0 до 1.0. Один недовольный клиент опускает водителя
на дно выдачи; один сговорчивый — поднимает на верх.

Соседний эндпоинт `rate-client` дубль проверяет (`routes/index.js:613`) — асимметрия, значит
просто забыли.

В PostgreSQL есть `UNIQUE(order_id)` (`schema.sql:107`), поэтому там накрутка не пройдёт —
но необработанное нарушение констрейнта уйдёт в общий обработчик ошибок и вернёт клиенту
`500 INTERNAL_ERROR` вместо понятного «уже оценено». А тесты гоняются на in-memory, где
констрейнта нет, и потому молчат.

**Что сделать.** Явная проверка в роуте + корректный код ответа:

```js
const existing = await db.ratings.byOrder(order.id);
if (existing) return res.status(409).json({ error: 'ALREADY_RATED' });
```

и `UNIQUE`-индекс продублировать в in-memory реализации, чтобы тесты ловили расхождение.

### H5 · ВЫСОКИЙ — в приложении нет удаления аккаунта → отклонение в Google Play

Бэкенд реализован полностью и грамотно — `DELETE /api/auth/account` с анонимизацией, и в
комментарии прямо написано «требование Google Play» (`src/routes/index.js:260`).

В приложении этот эндпоинт **не вызывается ни разу**. Поиск по всему `depanini-app` по
`auth/account` и `deleteAccount` — ноль совпадений. В `ProfileScreen` есть смена аватара,
язык, тема, тестовый пуш и выход — удаления нет.

Политика Google Play (Data deletion, действует с 2023) требует для приложений с аккаунтами
путь удаления **внутри приложения** плюс веб-ссылку. Это не «доработаем потом» — по этому
пункту приложение не пройдёт ревью на публикацию.

**Что сделать.** Пункт в `ProfileScreen` с двойным подтверждением → `DELETE /api/auth/account`
→ `clearToken()` → экран входа. Работы на полчаса, серверная часть готова. Плюс страница
с описанием процедуры удаления на публичном URL — её тоже требует форма подачи.

### H6 · ВЫСОКИЙ — позиция водителя перестаёт обновляться, как только он открывает навигатор

```js
// src/screens/DriverDashboardScreen.js:132–145
const { status } = await Location.requestForegroundPermissionsAsync();
const send = async () => {
  const loc = await Location.getCurrentPositionAsync({ accuracy: Location.Accuracy.High });
  await api.setLocation(loc.coords.latitude, loc.coords.longitude);      // REST
  socketRef.current?.emit('driver:location', { lat, lng });              // и то же самое сокетом
};
locTimer.current = setInterval(send, 5000);
```

Три проблемы в одиннадцати строках:

**Foreground-only.** Запрашивается только `requestForegroundPermissionsAsync`. В `app.json`
нет ни `ACCESS_BACKGROUND_LOCATION`, ни `FOREGROUND_SERVICE_LOCATION` для Android, а в
`UIBackgroundModes` для iOS — только `remote-notification`, без `location`. Как только водитель
блокирует экран или переключается в Google Maps (то есть **всегда**, потому что он едет),
JS-таймеры замирают. Клиент на экране отслеживания видит застывший грузовик — при том, что
экран отслеживания и есть главная ценность продукта для клиента.

**Двойная отправка.** Каждая позиция уходит и REST-запросом, и через сокет. Оба пути делают
`UPDATE drivers SET lat=..., lng=...` — ровно вдвое больше записей в БД, чем нужно
(`routes/index.js:443` и `realtime.js:64`).

**Утечка интервала.** `startLocationUpdates()` присваивает `locTimer.current` без очистки
предыдущего, а `stopLocationUpdates()` не обнуляет ссылку. Вызов при инициализации
(`DriverDashboardScreen.js:55`) и последующее переключение режима создают два интервала —
позиция начинает уходить вдвое чаще, и так далее с каждым переключением.

**Что сделать.**
1. `expo-location` + `expo-task-manager`: `Location.startLocationUpdatesAsync` с
   `foregroundService` на Android и `pausesUpdatesAutomatically: false` на iOS. Это единственный
   способ, которым продукт вообще может работать.
2. Оставить один транспорт — сокет; REST-эндпоинт держать как фолбэк при обрыве сокета.
3. `distanceInterval: 50` вместо интервала по времени: стоящий в пробке эвакуатор перестаёт
   слать одинаковые точки, а едущий шлёт чаще 5 секунд.
4. В `startLocationUpdates` — `if (locTimer.current) clearInterval(locTimer.current)` первой строкой,
   в `stopLocationUpdates` — `locTimer.current = null`.

### H7 · ВЫСОКИЙ — при недоступности OSRM цена молча падает на 20–40%

```js
// src/services/routing.js:53–56
} catch (e) {
  const km = haversineKm(aLat, aLng, bLat, bLng);
  return { km: +km.toFixed(2), durationMin: null, source: 'haversine' };
}
```

Фолбэк сам по себе правильный — сервис не должен падать из-за чужого сервера. Проблема в том,
что это **денежный** путь: расстояние по прямой в городе систематически меньше дорожного на
20–40%, и на эту же величину занижается цена каждого заказа. Водитель везёт за 2 000 DZD то,
что стоит 3 000.

Условия, при которых это происходит, — не редкость, а норма:

- `OSRM_URL` по умолчанию — публичный демо-сервер OSM. Его условия использования не
  предполагают коммерческого трафика; блокировка по IP — вопрос времени.
- Таймаут 7 секунд; при мобильной сети из Алжира до европейского хоста промахи будут регулярно.
- `source: 'haversine'` записывается в `breakdown` заказа — но никто это поле не читает,
  алерта нет, в админке не видно.

**Что сделать.**
1. Поднять свой OSRM — контейнер с картой Алжира (~200 МБ) на том же сервере. Убирает и
   зависимость, и латентность, и юридический вопрос.
2. Метрика `pricing_fallback_total` и алерт, если доля haversine превышает 5% за 15 минут.
3. Коэффициент 1.3 к haversine-расстоянию, пока источник не OSRM. Лучше слегка завысить,
   чем систематически возить в убыток.
4. Кэшировать пары координат, округлённые до ~100 м, — как уже сделано в `geocode.js`.
   Заказы в городе идут по одним и тем же маршрутам.

### H8 · ВЫСОКИЙ — арабский язык без RTL

Приложение заявляет два языка, `ar` — один из двух рабочих в Алжире, все строки переведены.
При этом `I18nManager` не используется **нигде** — поиск по всему `depanini-app` даёт ноль
совпадений.

Что это значит на экране: весь интерфейс остаётся слева-направо. Строки арабского прижаты
влево вместо правого края, иконки и стрелки «назад» смотрят не туда, `flexDirection: 'row'`

зеркалятся. Формально язык поддержан, фактически — арабский интерфейс выглядит сломанным.

Отдельно: в `theme/fonts.js` грузится Inter — латинская гарнитура без арабского начертания.
Арабский отрисуется системным шрифтом, то есть по другим метрикам, чем заложены в вёрстке.

**Что сделать.**
1. `I18nManager.forceRTL(lang === 'ar')` + `Updates.reloadAsync()` при смене языка — RTL в
   React Native применяется только после перезапуска, это ограничение платформы.
2. Заменить `marginLeft`/`marginRight`/`left`/`right` на `marginStart`/`marginEnd`/`start`/`end` —
   они зеркалятся автоматически.
3. Добавить арабскую гарнитуру (Cairo, Tajawal) и выбирать по языку.
4. Иконки направления (`back`, стрелки в списках) — зеркалить через `scaleX: -1` при RTL.

### H9 · ВЫСОКИЙ — лимит запросов по IP + агрессивный опрос = 429 за оператором NAT

Лимит — 600 запросов в минуту **на IP** (`src/app.js:53`). Считаем расход одного водителя
с открытым приложением:

| Источник | Частота | Запросов/мин |
|---|---|---|
| `pendingOrders` + `activeOrder` (`DriverDashboardScreen.js:64`) | каждые 4 с | 30 |
| `setLocation` (`DriverDashboardScreen.js:143`) | каждые 5 с | 12 |
| **Итого** | | **~42** |

Клиент на экране отслеживания: `api.history()` каждые 4 секунды — ещё 15/мин, плюс
`nearbyDrivers` каждые 10 секунд на карте.

**14 водителей за одним публичным адресом исчерпывают лимит.** У алжирских мобильных операторов
CGNAT — норма: за одним адресом сидят тысячи абонентов. Дальше все они получают
`429 TOO_MANY_REQUESTS`, приложение молча глотает ошибку (`catch (e) {}` во всех опросах),

**Что сделать.**
1. `keyGenerator` по `req.auth.userId` для авторизованных маршрутов, по IP — только для
   `/auth/*`. Тогда лимит защищает от одного злоупотребляющего аккаунта, а не от оператора связи.
2. Убрать опрос там, где уже работает сокет: `pendingOrders`/`activeOrder` дублируют события
   `order:new` и `order:status`. Оставить один редкий опрос (30–60 с) как страховку от разрыва.
3. Показывать пользователю, что связь потеряна, вместо тихого `catch (e) {}`.

### H10 · ВЫСОКИЙ — деплой в продакшен без прогона тестов, и в `main` лежит падающий тест **[проверено]**

`.github/workflows/deploy.yml` на каждый push в `main` заходит по SSH, делает `git pull`,
`npm run migrate`, перезапускает PM2. Шага `npm test` нет. Нет и отдельного workflow с тестами —

```
Test Files  1 failed | 6 passed (7)
```

**Что сделать.**
1. Workflow `test.yml` на pull request и push, и `needs: test` у джобы деплоя.
2. Замокать `geocode.js` и `routing.js` в тестах — как уже сделано с `google-auth-library`

3. Пока моков нет — прописать `GEOCODE_TIMEOUT_MS=50` в скрипт `test` рядом с `OSRM_TIMEOUT_MS`.

### M1 · Google-аккаунты не находятся по email → дубли аккаунтов

`users.create` (путь Google) не заполняет колонку `email_lower`:

**Что сделать.** Добавить `email_lower` в INSERT `users.create`; для существующих строк —

(с проверкой на конфликты по уникальному индексу).

Рядом: `users.email` объявлена `NOT NULL` (`schema.sql:13`), а код пишет `payload.email || null`

### M8 · После переназначения водителя карта замирает: устаревшее замыкание

Сокет-эффект объявлен с пустым списком зависимостей, но читает `order.id` и `driver.driverId`

```js
  socket.on('driver:location', (data) => { if (data.driverId === driver.driverId) animateDriverTo(...); });

```

Когда `reassignNext()` находит другого водителя и создаёт новый заказ, обработчики продолжают

**Что сделать.** Держать актуальные значения в `ref` (`orderIdRef` уже есть — завести такой же
для водителя) и сравнивать с `ref.current`. При переназначении — `emit('unwatch:driver', old)`,

### M9 · Перебор водителей: гонка и мусор в истории клиента

`reassignNext()` может быть вызван из трёх мест одновременно: обработчик сокета
(`OrderTrackingScreen.js:111`), опрос каждые 4 с (`:124`) и таймер обратного отсчёта (`:142`).
Флаг `searchingRef` проверяется только в опросе — таймер тикает каждые 500 мс и при `left <= 0`
вызывает `reassignNext()` без всякой проверки, до того как `setSearching(true)` доедет до
следующего рендера.

Дальше каждая итерация:
- **отменяет** предыдущий заказ (`api.cancelOrder`) и создаёт новый. Клиент, у которого никто
  не ответил с пятого раза, получает в истории пять записей `cancelled` — притом что он ничего
  не отменял;
- дёргает 2 запроса к OSRM и 2 к Nominatim (внутри `createOrder`). Перебор десяти водителей —
  40 обращений к внешним сервисам на одну поездку.

**Что сделать.** Логику перебора перенести на сервер: один заказ, поле `driver_id` меняется,
статус остаётся `requested`, история клиента чистая. Это заодно снимает гонку — клиент
перестаёт управлять диспетчеризацией. На клиенте, до переезда, — защитить вход в
`reassignNext` синхронным флагом (`if (searchingRef.current) return; searchingRef.current = true`)
и очищать таймер перед вызовом.

### M10 · Смена языка не перерисовывает интерфейс

### M11 · `scryptSync` блокирует цикл событий

```js
// src/utils/password.js:9, 16

```

Синхронный scrypt с параметрами по умолчанию (N=16384) занимает ~80–100 мс CPU. Node

**Что сделать.** Асинхронный вариант — `crypto.scrypt` через `promisify`. Работа уходит в
пул потоков libuv, цикл событий свободен. Правка на три строки, интерфейс функций не меняется.

### M12 · Рассылка нового заказа перебирает все открытые сокеты

```js
// src/services/realtime.js:112–120
for (const [, socket] of io.of('/').sockets) {
  if (socket.user && socket.user.id === driverUserId) socket.emit('order:new', order);
}
```

Линейный перебор всех подключений на каждый заказ. При 2 000 онлайн-водителей — 2 000 итераций
ради одной отправки, в синхронном коде.

**Что сделать.** Socket.io для этого и придумал комнаты: `socket.join('user:' + user.id)` при
подключении и `io.to('user:' + driverUserId).emit(...)`. Константное время, минус цикл.

### M13 · Сбой сети при запуске выкидывает пользователя на экран входа

```js
// App.js:152–161
if (tok) {
  try { const me = await api.me(); ... }
  catch (e) { /* токен протух — обычный вход */ }
}
```

`catch` не различает `401 INVALID_TOKEN` и `NETWORK — нет связи с сервером`. Водитель в
зоне слабого покрытия открывает приложение, `/auth/me` не отвечает — и он оказывается на
экране входа, хотя токен валиден. Для приложения, которым пользуются на обочине, это худший
сценарий из возможных.

**Что сделать.** Разбирать `e.status`: `401` → выход, всё остальное → оставить сессию и
показать баннер «нет связи», роль взять из локального кэша.

### M14 · Телефоны всех водителей отдаются любому клиенту

`findNearbyDrivers` возвращает `phones: d.phones || []` (`src/services/drivers.js:35`) для
каждого водителя в радиусе 50 км — до создания заказа, без каких-либо условий. Достаточно
пройтись по координатной сетке Алжира и получить базу телефонов всех водителей сервиса.

**Что сделать.** Убрать `phones` из `nearby`; телефон отдавать только после принятия заказа
и только его участникам. То же касается `documents.selfie` — фото водителя стоит показывать
после назначения.

### M15 · Файлы лежат на локальном диске одного инстанса

`UPLOAD_DIR` по умолчанию — папка `uploads` рядом с кодом (`src/services/uploads.js:19`),
PM2 запущен в `fork` с `instances: 1` (`ecosystem.config.cjs`). Значит:

- горизонтально масштабироваться нельзя — второй инстанс не увидит файлы первого;
- переезд на новый сервер = потеря всех документов водителей, если не помнить про `rsync`;
- бэкапа нет, ротации нет: перезалитые документы остаются на диске навсегда;
- падение процесса = недоступность сервиса целиком (нет второго инстанса).

Плюс `fileFilter` доверяет `file.mimetype`, который приходит из запроса — расширение
выбирается по нему же. Реальные байты не проверяются.

**Что сделать.** S3-совместимое хранилище (в `.env.example` переменные уже заведены) —
и файлы переживают деплой, и инстансов можно поднять несколько. Проверять сигнатуру файла
по первым байтам, а не по заголовку. Чистить осиротевшие файлы при перезаливке документа.

### M16 · Пустое поле в админке тарифов обнуляет тариф

```js
// src/admin/index.html:353
if(el) body[key] = Number(el.value);       // Number('') === 0
```

Поле рендерится пустым, если ключа нет в настройках (`const val = s[key] != null ? s[key] : ''`).
Админ открывает вкладку «Тарифы», где `commissionRate` не показан, но `deliveryConfirmTimeoutMin`
пуст, жмёт «Сохранить» — и в базу уходит `0`. Zod пропускает: у всех тарифов `min(0)`.
`pricePerKm: 0` означает, что все поездки становятся бесплатными (до `minFare`), и заметят
это по выручке, а не по ошибке.

**Что сделать.** Пропускать пустые поля (`if (el && el.value !== '') ...`), поднять нижнюю
границу в схеме (`min(1)` для `pricePerKm`, `minFare`), показывать подтверждение при снижении
тарифа более чем вдвое. И вывести в форму недостающие ключи — `commissionEnabled`,
`commissionRate`, `commissionLimitDZD`, `deliveryConfirmTimeoutMin` сейчас управляются только
через API.

### M17 · Пуш-уведомления: нет пакетной отправки и очистки мёртвых токенов

`sendPush` шлёт по одному сообщению за запрос (`src/services/push.js:39`) и возвращает `res.ok`.
Expo отвечает `200` даже когда доставка не удалась — детали лежат в теле ответа
(`DeviceNotRegistered`, `MessageTooBig`), которое не читается. Квитанции (receipts) не
запрашиваются.

Следствие: токены удалённых приложений накапливаются в БД навсегда, каждый заказ тратит на них
запросы, а реальные ошибки доставки невидимы. Expo при большом проценте невалидных токенов
начинает ограничивать отправителя.

**Что сделать.** Батч по 100 сообщений (Expo это поддерживает), разбор тела ответа,
`push_token = NULL` при `DeviceNotRegistered`, опрос квитанций через 15 минут.

## 4. Низкие

### L1 · Ни одного атрибута доступности во всём приложении

Поиск по `accessibilityLabel` и `accessibilityRole` в `depanini-app` — ноль совпадений на
5 723 строки. Кнопки с одними иконками (`Icon name="back"`, звёзды рейтинга, переключатели
режима водителя) для TalkBack и VoiceOver — безымянные элементы. `hitSlop` тоже не используется
нигде: мелкие иконки трудно попасть пальцем в дождь на обочине.

**Что сделать.** `accessibilityLabel` + `accessibilityRole="button"` на все `TouchableOpacity`
без текста, `hitSlop={{top:8,bottom:8,left:8,right:8}}` на иконки меньше 44 pt.

### L2 · Дублирующийся ключ в объекте API

```js
// src/services/api.js:76 и 79
authGoogle: (profile) => request('/api/auth/google', { ... body: profile ... }),
...
authGoogle: (idToken, role, language) => request('/api/auth/google', { ... }),
```

Второй молча затирает первый. Работает верный вариант, но это ровно тот класс ошибок, который
ловит линтер за ноль усилий — а линтера в проекте нет ни в приложении, ни в бэкенде.

**Что сделать.** ESLint с `no-dupe-keys`, `no-unused-vars`, `react-hooks/exhaustive-deps`
(последний нашёл бы и M8) в оба репозитория, шагом в CI.

### L3 · Хуки после раннего выхода в `SafeMarker`

```js
// src/components/SafeMap.js:54–58
export const SafeMarker = ({ tracksViewChanges, children, ...props }) => {
  if (!MarkerLib) return null;              // ← выход до хуков
  const [tracking, setTracking] = React.useState(true);
```

Сейчас безопасно — `MarkerLib` вычисляется один раз при импорте и не меняется. Но это прямое
нарушение правил хуков: если условие когда-нибудь станет динамическим, React упадёт с
«Rendered fewer hooks than expected», и искать причину будут долго.

**Что сделать.** Перенести проверку после хуков или обернуть в отдельный компонент.

### L4 · Обязательные 2,6 секунды заставки

```js
// App.js:164
setTimeout(() => setShowSplash(false), 2600);
```

Таймер не зависит от готовности данных: даже если всё загрузилось за 200 мс, пользователь
ждёт. Для приложения экстренной помощи — где человек стоит на трассе со сломанной машиной —
это худшее место для украшательства.

**Что сделать.** Показывать заставку до готовности, но не дольше: `Math.max(0, 600 - elapsed)`.

### L5 · Тёмная тема игнорирует системную настройку

`ThemeContext` читает только собственный ключ из `AsyncStorage` (`src/ThemeContext.js:16`),
`useColorScheme()` не используется. Одновременно `app.json` жёстко задаёт
`"userInterfaceStyle": "light"` — значит нативные элементы (клавиатура, системные диалоги,
`ActionSheet`) останутся светлыми даже когда приложение в тёмной теме.

**Что сделать.** `userInterfaceStyle: "automatic"` в `app.json`, третий режим `system`
в настройке темы через `useColorScheme()`.

### L6 · Пользователю показываются служебные коды ошибок

`friendly()` в `LoginScreen.js:95` переводит пять кодов, остальные возвращает как есть.
Пользователь при попытке входа увидит в диалоге `VALIDATION_ERROR`, `TOO_MANY_AUTH_ATTEMPTS`
или `HTTP_500`. То же во всех остальных экранах: `Alert.alert(t('error'), e.message)`.

**Что сделать.** Единый словарь кодов ошибок в одном модуле с фолбэком на «Что-то пошло не
так, попробуйте позже» вместо сырого кода.

### L7 · Сборка iOS не воспроизводится из чистого клона

`app.json` ссылается на `"googleServicesFile": "./GoogleService-Info.plist"`, а `.gitignore`
этот файл исключает. `google-services.json` при этом закоммичен — то есть решение по двум
платформам разное, и iOS-сборка из свежего клона упадёт.

Отдельно: в закоммиченном `google-services.json` массив `oauth_client` **пуст**. Для
`@react-native-google-signin` на Android нужны записи с отпечатком сертификата — без них вход
через Google работать не будет.

**Что сделать.** Определиться: либо оба файла в репозитории (они содержат только клиентские
идентификаторы, не секреты), либо оба через EAS Secrets. Перевыпустить `google-services.json`
из Firebase после добавления SHA-1 подписи.

### L8 · Ошибки проглатываются повсеместно, отчётности нет

`catch (e) {}` и `catch {}` встречаются в обоих репозиториях десятками — в опросах, в отправке
пушей, в загрузке маршрутов. `AppErrorBoundary.componentDidCatch()` пуст (`App.js:70`).
Sentry или аналога нет. Когда у водителя что-то не работает, узнать об этом можно только
от него самого.

**Что сделать.** Sentry (`sentry-expo`) в приложении и `@sentry/node` в бэкенде. Как минимум —
логировать проглоченные ошибки локально, чтобы их можно было забрать из устройства.

### L9 · Документация разошлась с кодом

- README обещает 37 тестов — их 70.
- README описывает поток `requested → accepted → en_route → picked_up → delivered → completed`,
  в коде `requested → accepted → arrived → en_route → delivered → completed`. Статус `picked_up`
  остался в `CHECK`-ограничении схемы (`schema.sql:64`), но в `TRANSITIONS` его нет — мёртвое значение.
- README и `SECURITY.md` описывают in-memory как основное хранилище и Google-вход как «демо-режим»;
  и то и другое давно не так.
- `SECURITY.md` называет лимит «100 req/мин», в коде 600.
- В `.env.example` `CORS_ORIGINS=*` предложен как рабочее значение, `OSRM_TIMEOUT_MS=4000`
  расходится с кодом (7000).

**Что сделать.** Привести README и `SECURITY.md` в соответствие; удалить `picked_up` из схемы.
Расхождение в цифрах безопасности хуже отсутствия документа — на него будут ссылаться.

## Приложение: как проверялись находки

Три находки подтверждены запуском кода, а не чтением. Остальные — по исходникам.

**H1, H4** — интеграционный тест через `supertest` на реальном стеке приложения:
занятый водитель принимает второй заказ (201 вместо 409); десять оценок одного заказа
проходят и опускают рейтинг водителя с 5.0 до 1.0 при `ratingCount: 10`.

**H10** — `npx vitest run` на чистом клоне `main`: `1 failed | 69 passed`, длительность 24 с.
Тот же набор с `GEOCODE_TIMEOUT_MS=50` — `7 passed` за 1,55 с, что доказывает: падение вызвано
обращением тестов к живому Nominatim, а не логикой.

**C1, C3** — тест не писался, но по коду однозначно: в `watch:driver` нет ни одной проверки
прав (сравнить с `join:order` в том же файле, где она есть); в `cardHtml` нет ни одного вызова
экранирования при том, что все поля приходят из открытой формы регистрации водителя.

Проверочный тест лежал во временной папке и в репозиторий не коммитился — он нужен был для
подтверждения находок, а не как постоянная часть набора. При исправлении H1 и H4 стоит завести
на них регрессионные тесты в `tests/`.
