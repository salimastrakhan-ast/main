# Архитектура

## Почему не как у Телеграма

Сервер Телеграма — закрытый код на C/C++ с самописными базами, собственным
бинарным протоколом MTProto и собственным языком описания API. Это результат
десяти лет работы и конкретных людей; повторять его для нового мессенджера —
способ не запуститься никогда.

Здесь взяты три архитектурных решения оттуда и ничего больше:

1. **Одно постоянное соединение с бинарным конвертом** вместо REST на каждый
   чих. Только не свой MTProto, а WebSocket.
2. **Умный клиент с локальной базой.** История лежит на устройстве, сервер
   досылает дельту. Отсюда мгновенный интерфейс и работа в метро.
3. **Шардирование по пользователю заложено с самого начала.** Сейчас один
   инстанс, но идентификаторы — UUID, а рассылка идёт через Redis, поэтому
   второй инстанс добавляется без переделки.

Всё остальное — обычное и наёмное: Go, Postgres, Redis, S3, Flutter.

## Из чего состоит

```
Flutter (iOS / Android / веб)
        │
        │  WebSocket + JSON — всё живое общение
        │  REST — вход, история, файлы
        ▼
Go: cmd/api  (HTTP и WebSocket на одном порту)
        │
        ├── internal/auth      вход по номеру, токены
        ├── internal/realtime  соединения, рассылка, presence
        ├── internal/store     весь SQL
        ├── internal/media     файлы
        └── internal/push      уведомления офлайн-адресатам
        │
   ┌────┴──────┬───────────┐
   ▼           ▼           ▼
Postgres     Redis       S3 / MinIO
переписка   рассылка      файлы
            лимиты
            presence
```

## Три решения, на которых всё держится

### Счётчик изменений в чате

`chats.last_seq` растёт на каждое изменение: новое сообщение, правку,
удаление. Клиент хранит курсор и после обрыва связи добирает ровно
пропущенное.

Без курсоров доставка держится на честном слове сокета, а сокет в мобильной
сети рвётся постоянно. Подробности — в [протоколе](protocol.md).

### Идемпотентность отправки

`UNIQUE (chat_id, sender_id, client_msg_id)`. Клиент придумывает
идентификатор до отправки и повторяет с тем же при обрыве. Повтор возвращает
уже созданное сообщение.

### Локальная база как источник правды на клиенте

Экраны подписаны на SQLite, а не на сокет. Сокет только пишет в базу.
Отправляемое сообщение сразу ложится в базу и рисуется, а очередь дотаскивает
его до сервера в фоне.

## Рассылка событий

Канал в Redis — на пользователя, а не на чат.

Подписок у инстанса тогда ровно столько, сколько у него живых соединений, а
не сумма их чатов. И человек, которого только что добавили в группу,
начинает получать её события без переподписки.

Событие едет по Redis ещё не закодированным: кодек выбирается на стороне
соединения. Поэтому один инстанс может обслуживать клиентов на разных
версиях протокола.

## Присутствие

Ключ `presence:<user_id>` в Redis с TTL 90 секунд, инстанс продлевает его
раз в 30. Упавший инстанс перестаёт держать своих пользователей «в сети» сам
по себе, без чужого вмешательства.

Presence рассылается только тем, с кем человек состоит в чатах.

## Что специфично для России

- **Вход по номеру `+7` в любой записи.** `8 (999) 123-45-67`, `+7 999…`,
  `9991234567` — всё это один аккаунт. Иначе человек заведёт три.
- **SMS через российского провайдера.** Через зарубежные шлюзы российские
  номера доходят плохо и дорого. Реализация для sms.ru есть, SMSC
  подключается так же — меняется URL и имена параметров.
- **Пуши без Google.** На новых Android в России нет сервисов Google, поэтому
  FCM для них не работает. Нужна связка RuStore Push и APNs. Интерфейс и
  точка вызова готовы, реализации провайдеров — отдельный этап.
- **Никаких чужих CDN в клиенте.** Движок отрисовки и шрифт лежат в сборке.
  Проверено: при недоступном `fonts.gstatic.com` приложение показывало белый
  экран пятнадцать секунд, при недоступном `www.gstatic.com` — навсегда.
- **Хранилище файлов на S3.** Yandex Object Storage, VK Cloud и Selectel
  говорят на этом протоколе, код между ними не меняется.

## Что сознательно отложено

Не потому что забыто, а потому что удвоило бы срок первой версии.

| Что | Почему отдельно |
|---|---|
| Каналы | Другая модель доставки: не рассылка при записи, а чтение по запросу |
| Секретные чаты с E2EE | X3DH и двойной храповик, отдельный большой этап |
| Групповые звонки | Сведение потоков на отдельном сервере; один на один уже есть |
| Боты и платежи | После того как ядро стабилизируется |
| Реальные пуши | Аккаунты у RuStore и Apple, отдельная работа |
| Шардирование по ДЦ | Заложено ключами, но не делается сейчас |

## Что стоит сделать до продакшена

Честный список того, чего в этой версии нет:

- **Полнотекстовый поиск по переписке.** Сейчас его нет вовсе.
- **Уборка мусора.** Вложения, загруженные и не прикреплённые к сообщению,
  остаются в хранилище навсегда. Нужен фоновой сборщик — индекс
  `attachments_orphan_idx` под него уже есть.
- **Ограничение частоты команд в сокете.** Лимиты стоят на входе, но
  подключившийся клиент может слать сообщения без ограничений.
- **Метрики и трассировка.** Логи есть, метрик нет.
- **Резервное копирование Postgres** и проверка восстановления.
- **Двухфакторный вход** поверх кода из SMS.
