# Протокол

Всё живое общение идёт по одному WebSocket-соединению. REST оставлен для
того, что либо предшествует соединению (вход), либо плохо ложится на кадры
(постраничная история, загрузка файлов).

## Конверт

```json
{"v": 1, "t": "message.send", "id": "c-42", "d": {}}
```

| Поле | Смысл |
|---|---|
| `v` | Версия протокола. Сейчас `1`. Расхождение видно сразу, а не в виде странных ошибок разбора |
| `t` | Тип команды или события |
| `id` | Идентификатор запроса. Клиент придумывает его сам, сервер возвращает в ответе. У событий пустой |
| `d` | Данные |

Кодирование живёт за интерфейсом `ws.Codec`. Сейчас реализация одна, JSON:
его видно в логах глазами и не нужен codegen в сборке клиента. Когда трафик
станет дорогим, рядом встанет реализация на Protobuf — обработчики команд при
этом не изменятся.

## Подключение

```
GET /v1/ws
```

Токен проверяется не заголовком, а первым кадром: браузерный WebSocket не
умеет слать `Authorization` при подключении.

```json
{"v":1,"t":"auth","d":{"token":"<access token>"}}
```

До этого кадра сервер не принимает ничего и через десять секунд закрывает
соединение. В ответ приходит `ready` с профилем.

Дальше клиент обязан прислать `sync` — иначе он не узнает о том, что
произошло, пока его не было.

## Команды

| Команда | Данные | Ответ |
|---|---|---|
| `auth` | `token` | `ready` |
| `sync` | `cursors: {chat_id: seq}` | `sync.result` |
| `message.send` | `chat_id` или `peer_id`, `text`, `client_msg_id`, `reply_to_id?`, `attachment_ids?` | `ack` с сообщением |
| `message.edit` | `chat_id`, `message_id`, `text` | `ack` |
| `message.delete` | `chat_id`, `message_id` | `ack` |
| `message.forward` | `from_chat_id`, `message_id`, `to_chat_id` или `to_peer_id`, `client_msg_id` | `ack` с сообщением |
| `read` | `chat_id`, `up_to_seq` | `ack` |
| `typing` | `chat_id` | нет |
| `chat.create` | `title`, `member_ids` | `ack` с чатом |
| `chat.addMember` | `chat_id`, `user_ids` | `ack` |
| `chat.leave` | `chat_id` | `ack` |
| `chat.removeMember` | `chat_id`, `user_id` | `ack` |
| `chat.delete` | `chat_id`, `for_everyone?` | `ack` |
| `call.start` | `chat_id` или `peer_id`, `sdp` | `ack` с `call_id`, `chat_id`, `status` |
| `call.answer` | `call_id`, `sdp` | `ack` |
| `call.ice` | `call_id`, `candidate`, `sdp_mid?`, `sdp_m_line_index?` | нет |
| `call.hangup` | `call_id`, `reason?` | `ack` |
| `ping` | — | `pong` |

`typing` — единственная команда без подтверждения: подтверждать каждое
нажатие клавиши значит удвоить трафик ради ничего. Ошибку клиент всё же
получит и на неё.

`message.send` принимает либо `chat_id`, либо `peer_id`. Во втором случае
личный чат заводится на лету — отдельной кнопки «создать диалог» в
мессенджере нет. То же у `call.start`: позвонить можно человеку, которому
ещё не писал.

`call.ice` — вторая команда без подтверждения: кандидатов за звонок
набираются десятки, и ответ на каждый удвоил бы трафик самой болтливой
части согласования.

`status` в ответе на `call.start` — `ringing` или `offline`. Второе
означает, что у собеседника нет живого соединения: держать человека сорок
секунд у гудков в пустоту незачем.

## События

| Событие | Когда |
|---|---|
| `message.new` | Новое сообщение в чате, где вы состоите |
| `message.edited` | Кто-то отредактировал сообщение |
| `message.deleted` | Кто-то удалил сообщение |
| `read.update` | Собеседник продвинул курсор прочитанного |
| `typing` | Собеседник печатает |
| `presence` | Собеседник появился или ушёл |
| `chat.update` | Новый чат, изменение состава или ваш выход (`gone: true`) |
| `call.incoming` | Вам звонят: `call_id`, `chat_id`, `from`, `sdp` |
| `call.accepted` | Собеседник снял трубку: `call_id`, `sdp` |
| `call.ice` | Очередной способ дозвониться от собеседника |
| `call.ended` | Звонок закончился: `call_id`, `reason` |

События приходят и на другие ваши устройства: с телефона отправили — на
десктопе видно. В то же соединение, откуда пришла команда, эхо не идёт:
подтверждения достаточно.

## Пересылка

`message.forward` делает **копию**, а не ссылку: оригинал могут удалить, и
пересланное не должно исчезать следом — человек переслал то, что видел.
Вложения копируются строками, объект в хранилище тот же, повторной загрузки
нет; из-за этого будущая уборка осиротевших файлов обязана считать ссылки.

Пересылающий должен состоять в обоих чатах — и в исходном, и в целевом.
Иначе знать чужой `chat_id` было бы достаточно, чтобы вытащить чужую
переписку в свою.

Копия помнит первого автора (`forwarded_from`) и его имя снимком
(`forwarded_name`): получатель может быть с ним незнаком, и разрешить
идентификатор ему нечем. Пересылка пересланного сохраняет именно первого —
цепочка «переслал того, кто переслал» никому не нужна.

Служебные записи (звонки) не пересылаются: «исходящий звонок» в чужой
переписке не значит ничего.

## Права в группе

Добавляет и исключает участников владелец или админ; владельца не исключает
никто — иначе админ выставил бы из группы того, кто её создал, и вернуть его
было бы некому. Себя исключить нельзя: для этого есть `chat.leave`, и это не
формальность — уход и исключение читаются по-разному.

`chat.delete` без `for_everyone` — это выход из чата: переписка остаётся у
второй стороны. С `for_everyone` она удаляется целиком, вместе с
сообщениями, и доступно это только владельцу группы. В личной переписке
`for_everyone` отклоняется: стереть историю у собеседника без его ведома —
не то, что человек вправе сделать чужими руками.

Объекты вложений в хранилище при удалении чата остаются: их уборка —
отдельная забота, иначе удаление держало бы транзакцию на время обхода
хранилища.

## Звонки

Сервер в звонке — только посредник. Он сводит две стороны, пересылает им
SDP и ICE-кандидатов и не разбирает их содержимое: это описания соединения
для WebRTC, понимать их должны клиенты. Звук через сервер не идёт — он идёт
напрямую между устройствами или, если сеть не даёт, через TURN.

```
звонящий                сервер                собеседник
   |  call.start (sdp)    |                        |
   |--------------------->|  call.incoming (sdp)   |
   |  ack call_id         |----------------------->|
   |<---------------------|                        |
   |                      |   call.answer (sdp)    |
   |  call.accepted (sdp) |<-----------------------|
   |<---------------------|                        |
   |  call.ice  <----------------------->  call.ice|
   |             (в обе стороны, пока идёт подбор) |
   |  call.hangup         |                        |
   |--------------------->|    call.ended          |
   |                      |----------------------->|
```

Причины в `reason`: `hangup`, `declined`, `missed`, `busy`, `failed`.

Реле работает только между двумя участниками записи о звонке — посторонний
с угаданным `call_id` получает `forbidden`. Размер SDP ограничен 16 КБ,
кандидата — килобайтом: без предела сокет стал бы каналом передачи чего
угодно мимо всех ограничений на вложения.

Адреса STUN и TURN клиент берёт у `GET /v1/calls/ice` перед каждым
звонком: пароль к TURN выписывается временный и живёт часы.

По окончании звонка сервер кладёт в переписку служебное сообщение
`kind: "call"` с `payload: {reason, seconds}`. Клиенты рисуют его отдельной
строкой, а не пузырём: его никто не писал.

## Синхронизация

Это самая важная часть протокола, и устроена она так.

У каждого чата есть `last_seq` — монотонный счётчик **изменений**. Номер
получает не только новое сообщение, но и правка с удалением. Сообщение
хранит два номера:

- `seq` — позиция в ленте, у правки не меняется;
- `updated_seq` — номер последнего изменения.

Порядок в интерфейсе строится по `seq`, синхронизация — по `updated_seq`.
Из-за этого клиент, который был офлайн, узнаёт не только о пропущенных
сообщениях, но и о том, что кто-то отредактировал старое. Со счётчиком
только по новым сообщениям правка осталась бы невидимой навсегда.

Клиент хранит по каждому чату курсор и при подключении присылает их все:

```json
{"v":1,"t":"sync","id":"c-1","d":{"cursors":{"<chat_id>": 42}}}
```

В ответ — список диалогов целиком (чтобы узнать о новых чатах и пересчитать
непрочитанное) и дельта по каждому отставшему чату:

```json
{"v":1,"t":"sync.result","id":"c-1","d":{
  "chats": [],
  "deltas": [{"chat_id": "…", "messages": [], "truncated": false, "last_seq": 45}]
}}
```

`truncated: true` означает, что пропущено больше, чем влезло в один ответ, и
остаток надо дочитать через `GET /v1/chats/{id}/messages`. Курсор в этом
случае двигать нельзя: в ленте дыра.

## Идемпотентность отправки

`client_msg_id` клиент генерирует **до** отправки. В базе стоит
`UNIQUE (chat_id, sender_id, client_msg_id)`, поэтому повтор возвращает уже
созданное сообщение, а не вторую копию.

Это не мелочь: клиент повторяет отправку при каждом обрыве связи, и без
этого правила чат заполнялся бы дублями. При конфликте транзакция
откатывается вместе с выданным номером, поэтому ретраи не оставляют дырок в
нумерации.

## Ошибки

```json
{"v":1,"t":"error","id":"c-42","d":{"code":"forbidden","message":"Нет доступа"}}
```

| Код | Значение | Повторять? |
|---|---|---|
| `bad_request` | Кривые данные команды | Нет |
| `unauthorized` | Токен не годится | Нет, нужен новый вход |
| `forbidden` | Нет доступа к чату или сообщению | Нет |
| `not_found` | Не найдено | Нет |
| `conflict` | Конфликт состояния | Нет |
| `rate_limited` | Слишком часто | Да, позже |
| `internal` | Ошибка сервера | Да |

## REST

| Метод и путь | Зачем |
|---|---|
| `POST /v1/auth/request-code` | Запросить код на номер |
| `POST /v1/auth/verify` | Обменять код на пару токенов |
| `POST /v1/auth/refresh` | Обновить пару |
| `POST /v1/auth/logout` | Отозвать устройство |
| `GET /v1/users/me`, `PATCH /v1/users/me` | Профиль |
| `PUT /v1/users/me/avatar`, `DELETE /v1/users/me/avatar` | Фото профиля; принимается только `image/*` |
| `GET /v1/users/search?q=` | Поиск по имени, нику и номеру телефона целиком |
| `GET /v1/contacts`, `POST /v1/contacts/sync` | Адресная книга |
| `POST /v1/devices/push-token` | Токен для пушей |
| `GET /v1/chats` | Список диалогов |
| `GET /v1/chats/{id}/messages?before_seq=&limit=` | Страница истории |
| `GET /v1/chats/{id}/members` | Участники |
| `GET /v1/calls/ice` | Адреса STUN и TURN с временным паролем |
| `POST /v1/media/upload` | Загрузить файл |

Поиск по номеру работает только при совпадении целиком: по части номера не
ищется намеренно. Имя и ник ищутся по вхождению, подстановочные знаки в
запросе обезврежены — иначе двух символов хватало бы, чтобы выгрузить
список людей по частям.

Синхронизация контактов возвращает только тех, кто уже зарегистрирован.
Номера незарегистрированных людей сервер не хранит: они не давали на это
согласия, а пользы от них никакой.
