# Типовые проблемы

Отсортировано по тому, как часто встречается на практике.

---

## Логин проходит, сервер виден, но вход в мир висит на «Connecting...»

Причина в 95% случаев: игровой сервер отдаёт клиенту адрес `127.0.0.1`,
и клиент на другом компьютере пытается подключиться к самому себе.

```bash
cat dist/game/config/ipconfig.xml
```

В атрибуте `address` должен стоять адрес, по которому машину видят игроки.
Правится в `.env` (`L2_EXTERNAL_IP`), затем:

```bash
make configure && make restart
```

---

## Список серверов пуст / сервер «на техобслуживании»

Игровой сервер не зарегистрировался на логин-сервере.

```bash
make logs-login | tail -30
make logs | grep -iE 'login|register'
```

Что смотреть:

- игровой сервер вообще запустился? `make status`;
- в `dist/login/config/Server.ini` должно быть
  `AcceptNewGameServer = True` — иначе регистрацию нужно подтверждать вручную;
- `RequestServerID` в `Server.ini` не должен конфликтовать с уже занятым
  номером в таблице `gameservers`.

Сбросить регистрацию и дать серверу зарегистрироваться заново:

```bash
docker compose exec db mariadb -uroot -p"$DB_ROOT_PASSWORD" "$DB_NAME" \
  -e "DELETE FROM gameservers;"
make restart
```

Заодно удали `dist/game/config/hexid.txt`, если он появился: в нём лежит
идентификатор прошлой регистрации.

---

## «Неверный логин или пароль» при первом входе

При `AutoCreateAccounts = True` аккаунт заводится при первом входе.
Если он всё же не создаётся:

```bash
make logs-login | tail -30
./scripts/account.sh accounts
```

Частые причины: логин-сервер не достучался до своей базы (проверь
`URL`/`Login`/`Password` в `dist/login/config/Database.ini`), либо
аккаунт с таким логином уже есть, а пароль другой.

Пароли намеренно не выставляются скриптом: разные ревизии хэшируют их
по-разному, и вписанный руками хэш даёт ровно эту ошибку. Проще
переименовать аккаунт и зайти заново.

---

## Импорт базы падает на середине

Симптом: `make db-init` ругается на конкретный `.sql`.

Дампы L2J писались во времена MySQL 5.x. Современная MariaDB в строгом
режиме отвергает нулевые даты и неявные дефолты. Стенд заранее ставит
`sql_mode = NO_ENGINE_SUBSTITUTION` в [`mysql/my.cnf`](../mysql/my.cnf) —
если ошибка всё равно про строгий режим, проверь, что конфиг подхватился:

```bash
docker compose exec db mariadb -uroot -p"$DB_ROOT_PASSWORD" \
  -e "SELECT @@sql_mode;"
```

Если там длинная строка со `STRICT_TRANS_TABLES` — файл не примонтировался,
проверь путь в `docker-compose.yml`.

Важно: импорт, упавший на середине, оставляет базу неконсистентной.
Скрипт в этом случае останавливается с ошибкой намеренно — почини причину
и запусти `make db-init` заново целиком.

## Сервер не стартует, в логе SQLException

```bash
make logs | head -40
```

Проверь по порядку:

1. база поднялась: `docker compose ps db` → healthy;
2. пароль в `.env` и в `dist/game/config/Database.ini` совпадают
   (после смены пароля в `.env` нужен `make configure`);
3. базы созданы и наполнены: `make db-init`;
4. `URL` указывает на хост `db`, а не `localhost` — внутри контейнера
   `localhost` это сам игровой сервер.

---

## «Port is already allocated» при запуске

Порт занят другим процессом (часто — прошлым запуском сервера).

```bash
sudo ss -tlnp | grep -E '2106|7777|3306'
```

Либо освободи порт, либо поменяй в `.env` (`LOGIN_PORT`, `GAME_PORT`,
`DB_PORT`) — только помни, что `LOGIN_PORT` должен совпадать с тем, куда
стучится клиент.

## Мобы ходят сквозь стены, персонажа откатывает назад

## Сервер замирает на секунду-две, потом отпускает

Паузы сборщика мусора. Диагностика и лечение —
[ANTI-LAG.md](ANTI-LAG.md), раздел 1.

Быстрая проверка:

```bash
make status | grep -A2 "паузы GC"
```

---

## Игровой сервер падает и перезапускается по кругу

```bash
make logs | grep -iE 'outofmemory|exception' | head -20
```

- `OutOfMemoryError` → мало кучи, подними `GAME_HEAP` в `.env`;
- ошибка загрузки данных → сборка собралась не полностью, `make build`;
- ошибка в скрипте квеста → выключить проблемный скрипт или обновить сборку.

Контейнер перезапускается сам (`restart: unless-stopped`) — это задумано,
но бесконечный цикл рестартов означает, что причина не устранена.

---

## После обновления эмулятора пропали настройки

Так и должно быть: `make build` заменяет `./dist` целиком, а прежние конфиги
складывает в `backups/config-<дата>/`.

Настройки восстанавливаются одной командой:

```bash
make configure
```

Именно ради этого рейты живут в профиле, а не в правках конфигов руками.
Если что-то правилось напрямую в `dist/*/config` — перенеси это в
`config/profiles/x10-classic.conf`, чтобы больше не терять.

---

## `make configure` пишет, что ключа нет в сборке

```
Ключи, которых нет в этой сборке (3):
    ? Rates.ini: RateDropItems
```

Это нормально: у профиля есть ключи из разных поколений эмулятора, и
неподходящие пропускаются. Тревожиться стоит, только если пропущены
**все** ключи дропа сразу — тогда в твоей ревизии они называются иначе.
Как найти правильные имена — [`config/profiles/README.md`](../config/profiles/README.md).

Ошибка (не предупреждение) с пометкой «обязательный ключ отсутствует»
означает, что профиль не подходит к сборке — сервер настроен не будет,
это надо чинить.

## Сборка падает

**`invalid source release: 25`** — компилируется не тем JDK. Mobius Interlude
требует JDK 25. Стенд для того и собирает в контейнере с готовым JDK 25,
поэтому проверь, что не передан `--local`:

```bash
./scripts/build-server.sh          # в контейнере, JDK 25 берётся из образа
```

**`Could not find or load main class org.apache.tools.ant.launch.Launcher`** —
так выглядит попытка использовать системный ant Debian/Ubuntu вне его
окружения: там jar-ы разложены по системным каталогам и собираются в classpath
скриптом-обёрткой. Стенд этого не делает: ant скачивается с Maven Central
в `.sources/ant` (два jar-а, ~2 МБ) и запускается своим лаунчером напрямую.
Если Maven Central недоступен, скрипт возьмёт ant с хоста.

**Про JDK 25 на хосте.** Он нужен только для `--local`. По умолчанию сборка
идёт в контейнере, и ставить его не требуется. Учти побочный эффект:
`sudo apt install openjdk-25-jdk` меняет java по умолчанию в системе, что на
рабочей машине может повлиять на другие проекты. Если всё же ставишь,
проверь потом:

```bash
sudo update-alternatives --config java
```

**`Repository not found`** — проверь `L2_SOURCE_REPO` в `.env`. Исходники
Mobius живут на GitLab: `https://gitlab.com/MobiusDevelopment/L2J_Mobius.git`.

**`архив сборки не найден`** — ant отработал, но ZIP не появился. Цель ant
по умолчанию называется `cleanup`: она пакует результат в архив и удаляет
`build/dist`, поэтому стенд ищет именно ZIP на уровень выше каталога хроники:

```bash
ls -la .sources/emulator/build
```

**Кончилось место.** Репозиторий большой, поэтому выкладывается только нужная
хроника (`L2_SPARSE_CHECKOUT=1`). Освободить место после успешной сборки можно
так — на работу сервера это не влияет, только на возможность быстро пересобрать:

```bash
rm -rf .sources
```

## Команды стенда затрагивают чужие контейнеры

Симптом: `docker compose ps` в домашней папке показывает сервисы, которых
в стенде нет (kafka, postgres, чужие переменные окружения), или `make down`
трогает не то, что ожидалось.

Причина: на машине задана переменная `COMPOSE_FILE` либо в домашнем каталоге
лежит свой `docker-compose.yml`. `COMPOSE_FILE` перебивает выбор файла
в **любом** каталоге, поэтому обычный `docker compose down` может погасить
рабочий стек.

Проверить:

```bash
echo "COMPOSE_FILE=$COMPOSE_FILE"
ls -la ~/docker-compose.y*ml ~/compose.y*ml 2>/dev/null
```

Стенд от этого защищён: и `Makefile`, и скрипты вызывают compose с явным
`-f docker-compose.yml`, поэтому работают только со своими тремя сервисами
(`db`, `login`, `game`) независимо от окружения.

Но голые команды `docker compose ...`, набранные руками, защиты не имеют.
Если на машине крутится ещё один стек, держи правило: работай через
`make`, а `docker compose` вручную запускай только с явным `-f`.

## Ничего из перечисленного

Собери картину целиком и смотри по ней:

```bash
make status
make logs | tail -100
make logs-login | tail -50
docker compose logs db | tail -50
```

Полезный приём: переключиться на эталонный профиль и проверить,
воспроизводится ли проблема на ретейл-значениях.

```bash
./scripts/configure.sh --profile retail-x1 && make restart
```

Если на x1 проблема исчезла — дело в рейтах или нагрузке, а не в эмуляторе.
