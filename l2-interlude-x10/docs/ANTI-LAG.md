# Откуда берутся лаги и что с ними сделано

Когда на сервере L2 «лагает», причина почти никогда не в коде эмулятора.
Ниже — четыре реальных источника тормозов в порядке того, как часто они
встречаются, что в этом стенде сделано против каждого и как проверить,
что дело именно в нём.

---

## 1. Паузы сборщика мусора JVM

**Симптом.** Раз в несколько минут сервер замирает на 0,5–3 секунды.
Все игроки одновременно: скиллы не срабатывают, персонаж «резинит».
Между паузами всё идеально.

**Причина.** Игровой сервер держит в памяти десятки тысяч объектов —
персонажи, мобы, предметы, эффекты. Старые сборщики мусора для уборки
останавливают все потоки приложения. Чем больше куча, тем длиннее пауза:
на 8 ГБ с настройками по умолчанию Full GC — это секунды.

**Что сделано.** По умолчанию включён **generational ZGC** (`JVM_PROFILE=zgc`):
он убирает мусор параллельно с работой сервера, паузы — доли миллисекунды
и не растут с размером кучи. Это главное отличие Java 21 от Java 8,
на которой крутится большинство старых сборок.

Плюс три флага в [`jvm/gameserver.options`](../jvm/gameserver.options):

- `-XX:+AlwaysPreTouch` — вся куча забирается у ОС сразу при старте.
  Без него первые минуты после рестарта, когда заходит вся толпа, сервер
  подтормаживает на выделении страниц.
- `-XX:+PerfDisableSharedMem` — JVM перестаёт писать счётчики в файл в `/tmp`.
  Если там тормозит файловая система (типично для дешёвых VPS), поток
  застревает в safepoint и встаёт **весь** сервер. Классическая загадочная
  «икота» раз в минуту.
- `-XX:+UseStringDeduplication` — снимает сотни мегабайт на одинаковых
  строках (имена предметов, скиллов, NPC).

**Как проверить.**

```bash
make status          # покажет самую долгую паузу из последних записей
grep -i pause logs/game/gc.log | tail -20
```

Ориентиры: до 50 мс — норма, никто не заметит; 50–200 мс — заметно
чувствительным; больше 200 мс — жалобы на лаги.

**Если паузы всё же большие** — почти наверняка куче тесно. Подними
`GAME_HEAP` в `.env` и перезапусти. Куча должна быть примерно вдвое больше
пикового потребления: сборщику нужен запас для работы.

| Онлайн | GAME_HEAP | ОЗУ машины |
|---|---|---|
| до 50 | 2G | 4 ГБ |
| до 200 | 4G | 8 ГБ |
| до 500 | 6–8G | 16 ГБ |
| 1000+ | 12G+ | 32 ГБ |

Если ZGC по какой-то причине не подходит, есть запасной профиль:
`JVM_PROFILE=g1` в `.env`.

## 2. База данных с настройками по умолчанию

**Симптом.** Тормозит вход в игру, открытие склада, телепорт. Массово —
при старте сервера и в прайм-тайм. Между этими операциями всё нормально.

**Причина.** MariaDB «из коробки» держит буферный пул в 128 МБ и сбрасывает
журнал на диск при каждой транзакции. Игровой сервер пишет в базу постоянно:
инвентарь, скиллы, квесты, позиция при выходе. На пятистах игроках это сотни
операций в секунду, и каждая упирается в диск.

**Что сделано** — [`mysql/my.cnf`](../mysql/my.cnf):

- `innodb_buffer_pool_size = 2G` (меняется через `DB_BUFFER_POOL` в `.env`) —
  вся рабочая база держится в памяти;
- `innodb_flush_log_at_trx_commit = 2` — журнал сбрасывается раз в секунду,
  а не на каждый commit. При аварии ОС теряется до секунды игровых действий;
  для игрового сервера это правильный размен;
- `rewriteBatchedStatements=true` в строке подключения — пакетные сохранения
  улетают одним запросом вместо сотни;
- включён лог медленных запросов.

**Как проверить.**

```bash
docker compose exec db tail -50 /var/log/mysql/slow.log
```

Пусто — база не при чём. Если запросы есть, смотри, по какой таблице:
обычно это `items` или `character_skills`, и лечится увеличением
`DB_BUFFER_POOL`.

**Про диск.** Всё вышеперечисленное не спасёт на HDD. Для сервера с живым
онлайном SSD/NVMe обязателен — это не про «быстрее», а про «работает вообще».

## 3. Геодата

**Симптом.** Мобы ходят сквозь стены, стреляют через скалы, персонаж
«телепортируется» назад при беге, агро цепляется через этаж. Игроки
называют это лагами, хотя сеть и сервер в порядке.

**Причина.** Геодата — карта проходимости мира. Без неё сервер не знает
про стены и высоты и считает, что всё пространство пустое.

**Что сделано.** В профиле x10 включён `PathFinding = 2` (пошаговый поиск
пути по ячейкам) и прописан путь `./data/geodata/`. **Сами файлы геодаты
нужно положить самому** — они производные от клиента и в исходники
эмулятора не входят. См. [CLIENT-SETUP.md](CLIENT-SETUP.md).

**Важный нюанс производительности.** `PathFinding = 2` даёт правильное
поведение мобов, но стоит процессорного времени. Если CPU в потолке
при большом онлайне — попробуй `PathFinding = 1` (упрощённый поиск)
или увеличь буферы поиска пути в `GeoEngine.ini`. Порядок действий
всегда такой: сначала правильно, потом быстро.

**Как проверить.** Зайди ГМ-ом, встань за стеной от моба и агри его.
С геодатой он побежит в обход. Без неё — упрётся в стену или пройдёт сквозь.

## 4. Сеть и то, что лагами не является

**Симптом.** Лагает у одного-двух игроков, у остальных нет.

Это не сервер. Проверяется за минуту:

```bash
make status     # если онлайн стабилен и пауз GC нет — сервер здоров
```

Частые причины на стороне игрока: далёкий географически хост, Wi-Fi,
античит-обвязка в некоторых сборках клиента, антивирус, проверяющий `l2.exe`.

**Отдельно про хостинг.** Сервер в другой стране от игроков — это +80–150 мс
к каждому действию, и никакими настройками это не лечится. Для сервера
«для своих» хостинг выбирается по географии игроков, а не по цене.

## Порядок диагностики

Когда пришла жалоба «лагает», по шагам:

1. `make status` — сервер вообще жив, сколько онлайна, какие паузы GC.
2. Паузы GC больше 200 мс → поднять `GAME_HEAP`, проверить `JVM_PROFILE=zgc`.
3. `docker compose exec db tail -50 /var/log/mysql/slow.log` → поднять
   `DB_BUFFER_POOL`.
4. `docker stats` → упёрлись в CPU: смотреть `PathFinding`, число мобов
   на спавне, кастомные скрипты.
5. Всё чисто, а лаги у конкретных людей → сеть на их стороне.

Отдельный приём: переключиться на `retail-x1` и посмотреть, воспроизводится ли
проблема. Если на x1 всё хорошо, дело в рейтах и нагрузке, а не в эмуляторе.
